# Alerts v1 contract

`openember.msgs.alerts.v1` defines structured alert observations, events and complete publisher-scoped state. It is independent of log text and does not prescribe a robot response. The C++ binding target advertises `OPENEMBER_ALERTS_CONTRACT_VERSION=1`.

An observation key comprises source, device, control session and condition code. RAISED and REMINDER indicate an active condition, CLEARED indicates a condition no longer holds, and UNKNOWN indicates unavailable evidence. Zero/unspecified enums must not be interpreted as healthy. Severity WARNING/ERROR is independent of the chosen response. Observations carry source sample sequence, source timestamp and explicit clock domain, validity, numeric measurements, thresholds, units, reference frame and context. Invalid observations use finite placeholder numbers and valid=false; they must not assert an active or cleared condition. Source timestamps are not Header Unix timestamps.

`AlertEvent` carries the producer's observation plus a publisher-instance-local revision. `AlertState` is a complete replacement of that publisher instance's condition set, including empty sets and last CLEARED/UNKNOWN observations. It is not a fleet-wide replacement and does not erase other publishers' state. Session removal increments revision without fabricating a clear event. A restarted adapter uses a new publisher_instance; revisions are only comparable within the same instance. Header.sequence is the event revision for events, and heartbeat_sequence for state.

The default logical topics are `/alerts/events` and `/alerts/state` in the robot/namespace communication scope. There is no cross-topic delivery ordering guarantee. Consumers deduplicate by instance and revision; events at or below an already applied full-state revision cannot modify current state. New subscribers recover via periodic state, not retained event delivery. Equal-revision states may carry newer heartbeat sequences. Older snapshots must never overwrite newer state. Unknown fields are preserved by protobuf for forward evolution; unknown enums remain unknown.

An online publisher periodically refreshes heartbeat_sequence and advertises stale_after_ms. Consumers measure expiry on their own steady clock, without comparing Unix and simulation clocks. Expiry or online=false means source unavailable, not all conditions cleared. A heartbeat proves publisher availability, not source detector sampling freshness. Abrupt exit or loss of the final offline message is handled by expiry.

`rejected_events` counts events rejected by Manager, `history_gaps` counts bounded-history overflows detected by this adapter, and `publish_failures` counts local send failures. None is a subscriber delivery acknowledgment. Periodic state repairs current-state loss; durable history, application acknowledgment, replay and exactly-once semantics are outside v1. Each consumer owns response policies and actuator arbitration remains separate.

The current core adapter bounds text to256 bytes, uses bounded event history and registry, and emits C++ protobuf bindings. This addition does not define a fixed-memory Nanopb alert-state layout. Contract tests cover unknown fields, unspecified defaults, source-clock separation, observations and empty full state.
